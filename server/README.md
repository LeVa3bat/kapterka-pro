# Серверная часть «Каптёрка ПРО»

| Что | Где | Файлы |
|---|---|---|
| Оплата, лицензии, реестр бойцов, вступление в подразделение | Cloudflare Worker `kapterka-api` | `cloudflare/worker.mjs`, `cloudflare/wrangler.toml` |
| Правила доступа к базе | Firebase Firestore, проект `kapterka-pro` | `firestore/transition.rules`, `firestore/strict.rules` |

Секретов в репозитории нет и быть не должно.

## Как это защищено

- **Оплата.** Цену задаёт сервер. После оплаты сервер сам спрашивает ЮKassa, сверяет сумму,
  товар и бойца. Один платёж даёт одну лицензию, повторная проверка ничего не продлевает.
- **Продление.** Лицензия, срок бойца и задание на письмо записываются одним атомарным
  Firestore commit. Предусловия по версии документа защищают от потери дней при двух
  покупках одновременно; при конфликте сервер перечитывает данные и повторяет расчёт.
- **Автовыдача.** Webhook и резервная сверка ЮKassa используют тот же путь выдачи,
  что и клиентский `check`. Webhook не возвращает ключ или данные покупателя.
- **Лицензии.** Записи лежат в `srv_licenses` / `srv_fighters`, и приложения туда не имеют доступа.
  Старые коллекции `licenses` / `fighters` сервер не считает достоверными.
- **Синхронизация.** Каждый телефон получает анонимную личность Firebase. Сервер (`unit_join`,
  с ограничением числа попыток) записывает его участником подразделения. При строгих
  правилах (фаза B) данные подразделения доступны только его участникам.
- **Админ.** В приложении нет пароля. Сервер сверяет SHA-256 и выдаёт сессию на 15 минут.
  После 5 ошибок вход блокируется.
- Открытый ретранслятор в Telegram (`send_telegram`) убран.

## Автоматическая выдача и повтор писем

В личном кабинете ЮKassa настройте HTTP-уведомление `payment.succeeded` на адрес
`https://<адрес Worker>/yookassa/webhook`. Подходит и существующий адрес Worker
с `?action=payment_webhook`. Тело уведомления используется только для получения ID:
статус, сумма, товар, адрес почты и боец перечитываются через API с авторизацией магазина.
Webhook подтверждает получение кодом 200 после надёжной записи результата; при
временной ошибке API или базы возвращает 5xx, чтобы ЮKassa повторила уведомление.
Публичный `check` по-прежнему требует соответствующий `fighter_id` или токен веб-покупки.

`wrangler.toml` включает Cron каждые 5 минут. Он также восстанавливает пропущенные
покупки за последние 7 дней по времени списания (`captured_at`), даже если покупатель
не вернулся в приложение или webhook ещё не был настроен. Обрабатываются только
`succeeded`, `paid=true`, точный товар `kapterka_pro_30d`, действующий тариф и валидная
почта. Каждый кандидат дополнительно перечитывается по ID через API ЮKassa.
Фиксированное окно и курсор сохраняются в `srv_payment_reconciliation/succeeded`;
частично обработанная страница при ошибке повторяется целиком и не продлевает уже
выданные лицензии. За запуск читается одна страница по 3 платежа; после окончания
прохода новое окно перекрывает последние 7 дней. Долгий перерыв после ранее завершённой
сверки расширяет следующее окно до сохранённой границы, чтобы не пропускать период простоя.

Письма не задерживают ответ с лицензией. Задание сохраняется в серверной коллекции
`srv_license_deliveries` вместе с лицензией; первая отправка запускается через
`waitUntil`, повтор — через Cron, не более 3 писем за запуск. Ошибка почты и прерывание
Worker оставляют задание для следующей попытки. Аренда задания предотвращает обычные
параллельные отправки; после ошибки действует увеличивающийся интервал до 1 часа.
Состояние `SENT` означает, что почтовый сервис принял письмо. Если сервис принял его,
но запись результата оборвалась, повтор может прислать то же письмо ещё раз;
новый ключ и дополнительные дни при этом не создаются. Для старых лицензий без
задания первый повтор `check` или сверка создаст одно задание восстановления доставки.
Новых секретов, очередей и платных сервисов для этого не требуется. Коллекции закрыты
существующим правилом запрета доступа ко всем неизвестным путям; правила менять не нужно.

Для контроля смотрите ошибки Worker и поля `state`, `attempts`, `nextAttemptAt`,
`lastError` в серверной коллекции доставки, а также `lastError`, `cursor`,
`completedThrough` в состоянии сверки. Ключи и адреса покупателей не публикуйте.
Начальная сверка не ищет платежи старше 7 дней; для такого восстановления нужен
отдельный контролируемый backfill. Лимит по 3 записи оставляет запас под бесплатный
лимит Worker в 50 внешних запросов; при устойчивом объёме выше 3 новых платежей или
писем за 5 минут потребуется отдельно пересмотреть производительность.

Основание: [уведомления ЮKassa](https://yookassa.ru/developers/using-api/webhooks),
[списки объектов](https://yookassa.ru/developers/using-api/lists),
[актуальная OpenAPI-спецификация с captured_at](https://yookassa.ru/developers/api/yookassa-openapi-specification.yaml),
[атомарный Firestore commit](https://firebase.google.com/docs/firestore/reference/rest/v1/projects.databases.documents/commit)
и [предусловия записи](https://firebase.google.com/docs/firestore/reference/rest/v1/Precondition).

## Покупка с сайта и активация на Android

Сайт отправляет в POST `create` случайный `web_claim_token` (32–128 шестнадцатеричных
символов), без `fighter_id`. Сервер хранит в metadata только `web_claim_hash` SHA-256;
одновременная передача токена и бойца запрещена. Для POST `check` сайт передаёт тот же
токен. Токен нельзя помещать в URL. Покупка остаётся без привязки к браузеру: первый
Android `license_verify` атомарно привязывает ключ к своему бойцу. Второе устройство
не может выиграть одновременную привязку или заменить уже привязанного бойца.
При первой привязке оплаченные 30 дней добавляются к неиспользованному сроку этого
бойца; повторная привязка/проверка дни не добавляет. Без действующего остатка исходный
срок считается со списания платежа. Уже истёкший непривязанный ключ не активируется.

POST `license_status` принимает `license_key` и возвращает только `ok`, `active`,
`status`, `expires_at`, `activated_at` (время в миллисекундах Unix). Он не привязывает
устройство и не раскрывает почту, бойца или ключ; подходит для отображения срока
в браузере даже после активации на Android. Старые/Android-покупки без `web_claim_hash`
сохраняют прежний протокол `create` / `check`.

## Разовая настройка (владелец, через панели, секреты не пересылать в чат)

1. **Firebase → Authentication → Sign-in method → Anonymous → Включить.**
2. **Firebase → Настройки проекта → Сервисные аккаунты → «Создать закрытый ключ».**
   Скачается JSON-файл. Он нужен в двух местах:
   - GitHub → Settings → Secrets and variables → Actions → `FIREBASE_SERVICE_ACCOUNT`
     (вставить содержимое файла целиком);
   - Cloudflare → Workers → kapterka-api → Settings → Variables and Secrets →
     Secret `FIREBASE_SERVICE_ACCOUNT_JSON` (то же содержимое).
   После этого удалите файл с телефона или компьютера.
3. Cloudflare → kapterka-api → Secrets:
   - `ADMIN_PASSWORD` — пароль админ-панели, не короче 12 символов (либо, для
     продвинутых, `ADMIN_API_SECRET_SHA256` + `ADMIN_SESSION_SECRET`);
   - по желанию: `BREVO_API_KEY` + `EMAIL_SENDER_EMAIL` (письма с ключом),
     `TG_BOT_TOKEN` + `TG_ADMIN_CHAT_ID` (уведомления).
4. Cloudflare → My Profile → API Tokens → Create Token → шаблон **«Edit Cloudflare Workers»**.
   В GitHub Secrets добавить `CLOUDFLARE_API_TOKEN` (токен) и `CLOUDFLARE_ACCOUNT_ID`
   (Account ID с главной страницы Workers).

## Выкладка

- **Сервер:** Actions → «kapterka-api (Cloudflare Worker)» → Run workflow → deploy = true.
  Перед выкладкой прогоняются тесты. После выкладки выполняется живая проверка.
  Ключи для 3.5.0 не меняются.
- **Правила, фаза A:** Actions → «Firestore rules» → phase = `transition`. Выкладывается вместе с 3.6.
- **Правила, фаза B:** phase = `strict`. Только по команде владельца, когда почти все
  пользователи обновились. После этого версии ≤3.5.0 перестанут синхронизироваться,
  но их данные на телефонах сохранятся.

## Проверки

```
node server/cloudflare/worker.test.mjs                  # сервер, без сети
node .github/scripts/payment-live-check.test.mjs        # диагностика: ошибки не маскируются успехом
node .github/scripts/payment-browser-check.cjs          # Chromium, внешняя сеть полностью подменена
node .github/scripts/payment-live-check.mjs --require-fulfillment  # живые сервисы, без оплаты и писем
npx firebase emulators:exec --only firestore \
  --config server/firestore/firebase.json --project demo-kapterka \
  "node server/firestore/rules.test.mjs"                 # правила в эмуляторе
```

Сначала публикуется сервер, затем сайт. Живая проверка требует `health.fulfillmentVersion = 1`;
на старом сервере она намеренно завершается ошибкой. Доступность шлюза и почтового
ретранслятора не подтверждает реальное списание или попадание письма во входящие.

Старая проверка платежей в Google Apps Script не является резервом нового сервера:
её ошибки `invalid_credentials` относятся к отдельной автоматизации, а не к рабочему
секрету Cloudflare. После включения новой серверной сверки старый триггер следует
отключить в его проекте. Менять рабочие ключи или разворачивать `server/yookassa-webhook.js`
для исправления этого сбоя не нужно; этот старый обработчик не участвует в текущем Worker.
